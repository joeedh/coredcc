# Integration test app

Status: pressure-tested 2026-11-19 and revised. The record is at the end.

A small app that hosts coredcc the way faberforge will, so integration tests can drive
it and inspect it from outside the process. It lives in `apps/testapp/`.

## Goals
- Boot coredcc in a real Chromium page, with the WASM backend first and the N-API backend
  once litestl's N-API runtime merges.
- Let a test process outside the app drive it and read structured results back: resolve
  paths, get and set values, run commands, undo and redo, feed input events to tools,
  dump overlay draw lists, take screenshots.
- Let an agent or a developer attach to a running instance and poke at it the same way.
- Run several instances at once, from several worktrees, without them colliding.

## Non-goals
- A user-facing editor. The page is a viewport plus a property-sheet panel, nothing more.
- Pixel-exact rendering tests. Assertions are made on the `DrawList` and on data, and
  screenshots are for humans.
- Replacing the C++ unit tests or P4's headless C++ host. The test app covers what only a
  JS host can show: bindings, foreign interfaces, WebGPU overlay rendering, and the
  native addon loading alongside the UI.

## Shell: NW.js
**Decision:** NW.js (`nw@0.112.0-sdk`, the version faberforge pins), driven over the
Chrome DevTools Protocol (CDP).

Why NW.js over Playwright's Chromium:
- One page can load either backend. NW.js merges Node and the browser into one context,
  so the same page can `require()` the N-API `.node` addon or import the WASM module.
  Verified with both in one page. A Playwright page can't load a native addon, so native
  tests would need a second harness.
- That is how faberforge consumes sculptcore today, and how it will consume coredcc.
- faberforge already solved the launcher and profile problems in NW.js
  (`nwjs/launch.mjs`, `nwjs/profile_dir.mjs`, `nwjs/cdp.mjs`). We follow that design,
  with the fixes below.
- CDP is built in, so no extra debugging protocol is needed for transport.
- Playwright can still attach with `chromium.connectOverCDP` if a later test needs it
  (verified: it connects in 37 ms and `page.evaluate` works).

What we give up:
- Playwright's test runner, locators and automatic throwaway contexts. Tests talk to the
  app through the testbus, not the DOM, so locators aren't needed.
- CDP screenshots of a hidden window. See "Screenshots".

**Runtime facts that matter:**
- NW.js 0.112 embeds **Node 26.1** (modules 147, N-API 10) and Chromium 149, not Node 24.
- The addon built for NW.js links `node.dll`, so it doesn't load in plain Node 24. A
  Node-side unit test of the addon needs its own build.
- The app root does not need to be the repo root. `import(file:///...)`, `fetch(file://)`
  and `require()` of an absolute `.node` path all work. `apps/testapp/` loads build output
  from `build/`.

The page also runs in a plain browser with the WASM backend, for quick manual checks.
Tests don't depend on that. The static server must send COOP/COEP for `wasm-mt`. NW.js
doesn't need them: `SharedArrayBuffer`, shared memory and pthreads all work there without
cross-origin isolation (verified).

## WASM builds for the app
- `wasm-st` is built with `-sENVIRONMENT=web`, and `wasm-mt` with
  `-sENVIRONMENT=web,worker`.
- The default `ENVIRONMENT` fails to load in NW.js with `Failed to resolve module
  specifier 'module'`. The page has `process.versions.node`, so emscripten's Node code
  path runs and imports `createRequire` from `module`.

## Remote protocol: CDP plus a testbus
- **Transport is CDP.** Clients connect to the page target's WebSocket and call
  `Runtime.evaluate` with `awaitPromise`.
- **The app protocol is a testbus object**, `globalThis.coredccTest`.
  - Every method returns a **string**: `JSON.stringify(reply, replacer)`, where `reply` is
    `{ok: true, value}` or `{ok: false, error}`. The client parses it with a matching
    reviver.
  - We can't use `returnByValue` with plain objects. It fails with a CDP error on a
    bigint inside an object and on cycles. It drops `undefined`, turns NaN, ±Infinity and
    -0 into null or 0, and turns Map, Set, Date and typed arrays into plain objects.
  - The replacer tags bigint (`{$bigint: "..."}`), NaN, ±Infinity, -0, `undefined` and
    typed arrays. 64-bit ids and `StableRef`s are bigints, so this is required.
  - The client also turns `exceptionDetails`, CDP errors and a closed WebSocket into
    `{ok: false}` replies.
  - Every call has a client-side timeout. A promise that never settles, such as `frame()`
    waiting on a lost GPU device, otherwise hangs the test forever.
- **Large replies:**
  - Replies are capped at 16 MB. Above that the testbus fails with an error.
  - A 128 MB reply closed the WebSocket in testing.
  - `dump()` and `drawList()` take an `outPath` option: the page writes the payload with
    Node `fs`, and the reply carries only the path.
- **Methods:**
  - `info()`: protocol version, pid, profile dir, backend (`wasm-st`, `wasm-mt`, `native`),
    build id, device pixel ratio, viewport size, and the WebGPU adapter (vendor and
    `isFallbackAdapter`, or "none").
  - `reset(sceneName, args)`: rebuild a registered test scene.
  - `get(path)`, `set(path, value)`, `meta(path)`: datapath access.
  - `exec(invocation)`: run a command from its string form, `tool.path(k=v ...)`.
  - `undo()`, `redo()`, `history()`.
  - `input(events)`: feed synthetic `InputEvent`s straight to the ToolManager. They bypass
    the DOM, so they need no focused window. rAF keeps running in a hidden window (62/s
    measured), so this should be deterministic; it is still unverified.
  - `frame()`: run one update-and-draw cycle and resolve when it has finished.
  - `drawList(opts)`: the last overlay `DrawList`, decoded to JSON.
  - `dump(kind, opts)`: structured state dumps (library blocks, the graph, the scene).
  - `shot(opts)`: a PNG screenshot (see below).
- **The CDP client** is a dependency-free module (Node 22+ has global `fetch` and
  `WebSocket`). It is both a library for tests and a CLI:
  `node apps/testapp/cdp.mjs call info`, `call get '"scene.objects.length"'`,
  `eval "..."`, `shot out.png`.
- The protocol is versioned. A test checks `info().protocol` and fails clearly on a
  mismatch.

## Screenshots
- `Page.captureScreenshot` hangs in a window that has never been shown. It also hangs
  with `fromSurface: false`, when minimized, and after a show then a hide. Playwright's
  screenshot hangs the same way.
- `nw.Window.get().capturePage(cb, {format: 'png', datatype: 'datauri'})` works while the
  window is hidden, and includes the WebGPU canvas. **`shot()` uses it.**
- CDP capture is used only for windows that are actually shown.

## Logs and crashes
- NW.js renderer output never reaches the launcher. `console.log`, `console.error`,
  `process.stdout.write` and `fs.writeSync(1)` were all lost, whether stdio was piped or
  inherited, and with `--enable-logging=stderr`. Only the DevTools banner came through.
  faberforge's doc says otherwise; that may hold only with a real console attached.
- So:
  - The harness enables the CDP `Runtime` and `Log` domains, and records
    `Runtime.consoleAPICalled`, `Runtime.exceptionThrown` and `Log.entryAdded` as they
    arrive.
  - The C++ log sink also appends to `<artifacts>/log.txt` through Node `fs`, flushed per
    line, so a crash doesn't lose it.
- **A renderer crash makes the app exit with code 0.** The pending `evaluate` sees the
  WebSocket close, and the minidump lands in `<profile>\Crashpad\reports\*.dmp`.
  - The harness treats "WebSocket closed" as a crash, whatever the exit code.
  - Before deleting the profile, it copies the dumps and logs into a kept artifacts
    directory. When a test fails, it keeps the whole profile.

## Profiles, ports and instances
NW.js keys its default Chromium profile on the manifest `name`, which is the same in every
worktree.
- **A second launch on a profile that is already in use** prints `Opening in existing
  browser session.` and exits with code 0 within about 0.6 s, silently dropping its
  arguments. The launcher treats either that line, or an exit within a few seconds, as
  failure: "profile in use by PID X". Exit code 0 is never taken as success.
- **Test launches always get a throwaway profile:** a fresh `mkdtemp` directory under
  `os.tmpdir()`, prefixed `coredcc-testapp-`.
  - It is deleted after exit. In testing, deletion succeeded on the first try in every
    case, within 20–84 ms, including after kills and crashes. A short retry loop stays
    anyway.
  - No GPU, crashpad or utility processes outlived the browser process.
- **Manual launches get a per-worktree profile:**
  `%LOCALAPPDATA%\coredcc\testapp\<dir>-<hash8>\`, with `hash8` over the case-folded
  worktree root. `--instance=NAME` adds a named sub-profile, and a bare `--instance`
  adds a throwaway one.
- **Garbage collection** of throwaway profiles runs from both the launcher and the test
  harness. A runner that dies takes NW.js with it, because a non-`detached` child is in a
  kill-on-close job object, but its profile directory leaks.
  - A profile is dead only if deleting its `lockfile` succeeds. A live profile fails that
    with EPERM, and GC skips it.
  - A blind recursive delete of a live profile would remove the unlocked files and corrupt
    it, so it is never done.
- **Ports:**
  - The launcher passes `--remote-debugging-port=0`. It deletes any stale
    `DevToolsActivePort` before spawning, because the file survives a clean exit.
  - It takes the port from whichever comes first: the new `DevToolsActivePort` file (it
    appeared about 520 ms after spawn), or the `DevTools listening on ws://...` line on
    stderr.
  - It confirms the instance by checking that `info().pid` and `info().profile` match
    this launch.
  - In testing, 8 parallel launches got 8 distinct ports. Port 9222 is already in use on
    this machine by another NW.js app, which is why there is no fixed default.
- **No `--remote-allow-origins=*`.** faberforge passes it, but Node's `WebSocket` doesn't
  need it. With it, a WebSocket carrying `Origin: https://evil.example` opened CDP, so any
  web page that finds the port gets Node and therefore code execution. Without it, that
  connection was rejected.
- **Background launches:** the child stays non-`detached`, so it dies with the runner. If
  the CLI ever offers a background launch, it needs a `kill` subcommand by profile or PID.

## Determinism
- The launcher always passes `--force-device-scale-factor=1`. The device pixel ratio is
  2 on this machine, so without the flag viewport sizes, DrawList coordinates and
  screenshots vary by monitor.
- The viewport size is fixed in the manifest and reported by `info()`. A test can assert
  on it.

## Headless and GPU-less runs
- `--headless` maps to an app flag that keeps the window hidden (`show: false`).
  Chromium's real `--headless` is never passed: with it, `nw.App.quit()` leaves the
  process running.
- WebGPU works in a hidden window with no extra flags: adapter, device, rendering and
  `onSubmittedWorkDone` all worked.
- `--webgpu=swiftshader` maps to `--use-webgpu-adapter=swiftshader
  --enable-unsafe-webgpu`, which gives a working software adapter for machines with no
  GPU.
- With no adapter at all, `info()` reports "none", the renderer draws nothing, and
  `drawList()` still works.
- A test that needs rendering states which adapter it requires: real or software.
- The app's argument parser ignores unknown `--` switches. Chromium switches such as
  `--user-data-dir` show up in `nw.App.argv`.

## Layout
```
apps/testapp/
  package.json         nw, esbuild, typescript (pnpm)
  nwjs/
    launch.mjs         profile, port, flags; prints the profile and CDP port
    profile_dir.mjs    profile paths and GC
    window.html
  cdp.mjs              CDP client library and CLI
  src/
    main.ts            boot, backend selection, the frame loop
    backend/           wasm.ts, native.ts: same surface over the generated bindings
    testbus.ts         the testbus, reply encoding
    scenes.ts          registered test scenes
    overlay/           WebGPU renderer for DrawList
    panel/             property sheet built from a coredcc layout
  tests/
    tsconfig.json      erasableSyntaxOnly, verbatimModuleSyntax,
                       allowImportingTsExtensions, noEmit
    harness.ts         launch(), connect(), teardown, crash artifacts, profile GC
    *.test.ts
```
- **Tests use `node:test`**, and Node 24 runs `.ts` files directly with no flags.
  Type stripping has limits:
  - It rejects `enum`, `namespace`, parameter properties and `<T>x` assertions.
  - Imports must use `.ts` extensions. Types must be imported with `import type`.
  - It doesn't type-check, so `tsc -p apps/testapp/tests` runs as a separate check step.
- **Tests only `import type` from `src/` or the generated bindings.** litestl's TS
  runtime uses `export enum` and extensionless imports, so a value import of it or of any
  page module that pulls it in crashes under type stripping. Values cross only through
  the testbus.
- **Concurrency:** `node --test` runs files in parallel, with the default concurrency set
  by `availableParallelism` (16 here). Tests run with `--test-concurrency=4`. 8 at once
  worked; more wasn't tried.
- The page is bundled with esbuild.
- The C++ side the page needs (backend glue, test scenes that must be built in C++) lives
  in `source/coredcc/testapp/`, built only when the app is.

## Stages
- **TA0 (with P0):** the shell, launcher, profiles and GC, the CDP client, the reply
  encoding, log capture, crash artifacts, and a testbus with `info()` and `shot()`.
  No coredcc yet. Tests:
  - Launch two instances at once, call `info()` on both, and check that both profiles are
    deleted afterwards.
  - A second launch on a profile already in use fails loudly.
  - Round-trip the reply encoding: bigint, NaN, -0, `undefined`, typed arrays, an
    oversize reply.
  - `shot()` returns a PNG from a hidden window.
  - A forced renderer crash (`Page.crash`) is reported as a crash, and its dump is kept.
- **TA1 (P1 exit):** the WASM backend, `get`, `set`, `exec`, `undo` and `redo`. This is
  where P1's TS spike runs.
- **TA2 (P2):** the property panel built from a layout file.
- **TA3 (P4):** the WebGPU overlay renderer, `input`, `frame` and `drawList`, plus a gizmo
  drag-undo-redo test.
- **TA4 (after the N-API runtime merges):** the native backend, built for NW.js's Node 26
  runtime, with every TA1–TA3 test run against both backends.

## Pressure test record (2026-11-19)
A fresh agent was given this plan and the faberforge harness, but none of the author's
reasoning. It ran 59 NW.js launches across 14 experiments
(`scratchpad\testapp-pt\`). The original claims are listed with their outcomes.

### Survived
- NW.js 0.112 honours `--remote-debugging-port=0` and writes `DevToolsActivePort` into a
  custom `--user-data-dir`. 8 parallel launches got 8 distinct ports.
- Two NW.js instances with different profiles run side by side; 8 at once were ready in
  1.1–1.8 s.
- A throwaway profile can be deleted right after exit: it succeeded on the first try in
  every case, including kills, renderer kills, `Page.crash` and kills during WebGPU work.
- WebGPU is available in an NW.js window that is never shown, with no flags. The
  "no adapter" path is real (`--disable-gpu`), and SwiftShader works as a fallback.
- Node 24 runs `.ts` `node:test` files without flags.
- One page loads both an emscripten ES module and an N-API addon.
- Also confirmed: `wasm-mt` runs in NW.js without COOP/COEP; NW.js dies with the test
  runner; Playwright `connectOverCDP` attaches; NW.js keys its default profile on the
  manifest name; real `--headless` should be avoided.

### Broke, and what changed
- **CDP screenshots of a hidden window hang.** `shot()` uses `capturePage` instead.
- **`returnByValue` mangles or rejects ordinary values.** The testbus returns encoded
  JSON strings, the client applies its own timeout, and replies are capped at 16 MB with
  file output for large dumps.
- **The default emscripten `ENVIRONMENT` doesn't load in NW.js.** Builds for the app use
  `web` and `web,worker`.
- **Renderer output never reaches the launcher.** Logs go through CDP and a log file.
- **Type stripping can't load the page's modules or litestl's TS runtime.** Tests import
  types only, and `tsc` runs as a separate check.

### New findings that changed the plan
- NW.js embeds Node 26.1, so its addon build doesn't load in Node 24.
- `--remote-allow-origins=*` lets any web page reach CDP, and so Node. It is dropped.
- A launch on a profile already in use exits 0 and drops its arguments. The launcher now
  detects it.
- `DevToolsActivePort` survives a clean exit, so it is deleted before each launch.
- A live profile's `lockfile` can't be deleted, which GC uses as its liveness check.
- A renderer crash exits with code 0, and immediate profile deletion destroys the dump.
  Crash artifacts are now kept.
- The device pixel ratio varies by machine, so the launcher forces 1.
- Chromium switches leak into `nw.App.argv`, so the app ignores unknown switches.
- `node --test` defaults to 16 parallel files here, so concurrency is capped at 4.

### Still unverified
- `input()` is deterministic in a hidden, unfocused window. It depends on coredcc code
  that doesn't exist yet.
- Behaviour on a real CI machine with no GPU device. Only `--disable-gpu` was tried.
- What caused one 200 MB reply run to drop the connection and later exit the instance.
