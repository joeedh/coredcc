# Integration test app

Status: draft, not yet pressure-tested.

A small app that hosts coredcc the way faberforge will, so integration tests can drive
it and inspect it from outside the process. It lives in `apps/testapp/`.

## Goals
- Boot coredcc in a real Chromium page, with the WASM backend first and the N-API backend
  once litestl's N-API runtime merges.
- Let a test process outside the app drive it and read structured results back: resolve
  paths, get and set values, run commands, undo and redo, feed input events to tools,
  dump overlay draw lists, take screenshots.
- Let an agent or a developer attach to a running instance and poke at it the same way.
- Run several instances at once, from several worktrees, without them colliding.

## Non-goals
- A user-facing editor. The page is a viewport plus a property-sheet panel, nothing more.
- Pixel-exact rendering tests. Assertions are made on the `DrawList` and on data, and
  screenshots are for humans.
- Replacing the C++ unit tests or P4's headless C++ host. The test app covers what only a
  JS host can show: bindings, foreign interfaces, WebGPU overlay rendering, and the
  native addon loading alongside the UI.

## Shell: NW.js
**Decision:** NW.js (`nw@0.112.0-sdk`, the version faberforge pins), driven over the
Chrome DevTools Protocol (CDP).

Why NW.js over Playwright's Chromium:
- One page can load either backend. NW.js merges Node and the browser into one context,
  so the same page can `require()` the N-API `.node` addon or instantiate the WASM module.
  A Playwright page can't load a native addon, so native tests would need a second
  harness.
- That is how faberforge consumes sculptcore today, and how it will consume coredcc.
- faberforge already solved the launcher, profile and CDP problems in NW.js
  (`nwjs/launch.mjs`, `nwjs/profile_dir.mjs`, `nwjs/cdp.mjs`); we copy that design.
- CDP is built in, so no extra debugging protocol is needed for transport.

What we give up:
- Playwright's test runner, auto-waiting locators and automatic throwaway contexts. We
  don't need locators: tests talk to the app through the testbus, not the DOM.
- Playwright can still attach to NW.js with `chromium.connectOverCDP` if a later test
  needs it. Nothing below rules that out.

The page also runs in a plain browser (served statically) with the WASM backend, for
quick manual checks. Tests don't depend on that.

## Remote protocol: CDP plus a testbus
- **Transport is CDP.** The launcher passes `--remote-debugging-port`. Clients connect to
  the page target's WebSocket and use `Runtime.evaluate` with `awaitPromise` and
  `returnByValue`.
- **The app protocol is a testbus object**, `globalThis.coredccTest`, with JSON-in,
  JSON-out methods. Every reply is `{ok: true, value}` or `{ok: false, error}`, so a
  failure never becomes an exception that CDP reports differently.
  - `info()`: protocol version, backend (`wasm-st`, `wasm-mt`, `native`), build id.
  - `reset(sceneName, args)`: rebuild a registered test scene.
  - `get(path)`, `set(path, value)`, `meta(path)`: datapath access.
  - `exec(invocation)`: run a command from its string form, `tool.path(k=v ...)`.
  - `undo()`, `redo()`, `history()`.
  - `input(events)`: feed synthetic `InputEvent`s straight to the ToolManager. They bypass
    the DOM, so they are deterministic and need no focused window.
  - `frame()`: run one update-and-draw cycle and resolve when it has finished.
  - `drawList()`: the last overlay `DrawList`, decoded to JSON.
  - `dump(kind)`: structured state dumps (library blocks, the graph, the scene).
  - `log()`: drain the captured C++ and JS log lines.
- **Screenshots** use CDP's `Page.captureScreenshot`, not the testbus.
- **The CDP client** is a dependency-free module (Node 22+ has global `fetch` and
  `WebSocket`), as in faberforge's `cdp.mjs`. It is both a library for tests and a CLI:
  `node apps/testapp/cdp.mjs eval "..."`, `call get '"scene.objects.length"'`, `shot out.png`.
- The protocol is versioned. A test checks `info().protocol` and fails clearly on a
  mismatch.

## Profiles, ports and instances
NW.js keys its default Chromium profile (`--user-data-dir`) on the manifest `name`, which
is the same in every worktree. Two instances sharing a profile collide on the
single-instance lock, so the second launch just hands its arguments to the first.
- **Test launches always get a throwaway profile:** a fresh `mkdtemp` directory, deleted
  after the process exits. Deletion retries for a few seconds, because Windows keeps
  files locked briefly after exit.
- **Manual launches get a per-worktree profile:**
  `%LOCALAPPDATA%\coredcc\testapp\<dir>-<hash8>\`, with `hash8` over the case-folded
  worktree root, as faberforge does. `--instance=NAME` adds a named sub-profile, and a
  bare `--instance` adds a throwaway one.
- **A GC pass at launch** removes throwaway profiles older than a day whose owning process
  is gone.
- **Ports:** the launcher passes `--remote-debugging-port=0`, and Chromium then writes the
  chosen port to `DevToolsActivePort` in the profile directory. The launcher reads that
  file, so parallel launches never race for a port.
- App state such as settings never lives in the Chromium profile. The test app keeps none
  in v1.

## Layout
```
apps/testapp/
  package.json         nw, esbuild, typescript (pnpm)
  nwjs/
    launch.mjs         profile, port, flags; prints the profile and CDP port
    profile_dir.mjs
    window.html
  cdp.mjs              CDP client library and CLI
  src/
    main.ts            boot, backend selection, the frame loop
    backend/           wasm.ts, native.ts: same surface over the generated bindings
    testbus.ts
    scenes.ts          registered test scenes
    overlay/           WebGPU renderer for DrawList
    panel/             property sheet built from a coredcc layout
  tests/               node:test files (.ts run by Node's type stripping)
    harness.ts         launch(), connect(), teardown with profile cleanup
```
- Tests use `node:test`. Node 24 runs `.ts` files directly, so there is no build step for
  tests. The page itself is bundled with esbuild.
- The C++ side the page needs (backend glue, test scenes that must be built in C++) lives
  in `source/coredcc/testapp/`, built only when the app is.

## Headless runs
- `--headless` maps to an app flag that keeps the window hidden, as faberforge does. The
  real Chromium `--headless` switch is not used, because NW.js intercepts it.
- WebGPU needs an adapter. On a machine without one, the overlay renderer reports
  "no adapter" through `info()` and draws nothing. `drawList()` still works, because it
  doesn't depend on the renderer, so most tests still run.

## Stages
- **TA0 (with P0):** the shell, launcher, profiles, CDP client and a testbus that answers
  `info()` only. No coredcc yet. Test: launch two instances at once, call `info()` on
  both, and confirm both profiles are deleted afterwards.
- **TA1 (P1 exit):** the WASM backend, `get`, `set`, `exec`, `undo` and `redo`. This is
  where P1's TS spike runs.
- **TA2 (P2):** the property panel built from a layout file.
- **TA3 (P4):** the WebGPU overlay renderer, `input`, `frame` and `drawList`, plus a gizmo
  drag-undo-redo test.
- **TA4 (after the N-API runtime merges):** the native backend, with every TA1–TA3 test
  run against both backends.

## Claims to pressure-test
- NW.js 0.112 honours `--remote-debugging-port=0` and writes `DevToolsActivePort` into
  the given `--user-data-dir`.
- Two NW.js instances with different `--user-data-dir`s run side by side.
- The throwaway profile can be deleted within a few seconds of exit on Windows.
- WebGPU is available in an NW.js window that is never shown.
- Node 24 runs the `.ts` test files without flags.
- One page can load both an emscripten ES module and an N-API addon.
