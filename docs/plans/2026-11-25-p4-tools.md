### coredcc
- **`draw/` has only `View` and `ViewMath`** (`draw/view.h`). `scene/` depends on `draw/`
  (`scene/CMakeLists.txt`), so `draw/` can't use anything of `scene/`. A new `tool/` module can use both.
- **The Context has no ToolManager slot** (`api/context.h`). It has `executor()` and `scene()`.
- **Drags are P3's and work:** `core.object.dragDelta` makes an `ApplyDelta`, and a tool calls `update` with the
  total delta since the start (`scene/commands.h`). `startState`, `startPivot`, `count`, `object`,
  `changed`, `locked` and `driven` are what a gizmo needs. `computeState` and `computePivot` are in
  `scene/object.h`.
- **Scripts can't update a drag.** `ApplyDelta` has `defineBindings`, but no facade reaches it (no match for
  `drag` in `bind/*.h`). `writeInteractive` writes a path, which ApplyDelta's undo doesn't take back.
- **Every facade that changes the document is Busy inside any script slot but a Command's.**
  `detail::slotGate` (`bind/facades.cc:83`) allows a call when there is no foreign frame, or when the
  innermost frame is one of the listed Command slots. So a TS tool's `onEvent` couldn't `invoke`, `pick` or
  `evaluateScene` (`bind/scene_facades.cc` gates them to `exec`).
- **`detail::runCommand` runs a sub-command whenever any foreign call is in progress**
  (`bind/facades.cc`, after `slotGate`). From a tool's slot, which isn't inside a command, `runSub` would
  fail: it is allowed only from `exec`.
- **A script can't return an interface.** `foreignImplementable` refuses a returned pointer's ownership
  (`bind/foreign_command.h`). So `Gizmo::beginDrag` can't return a Modal; it pushes one itself.
- **`UndoHistory` has no interactive hooks.** The architecture lists `beginInteractive`, `commit` and `cancel`
  on it (§6). In the code the executor keeps the open record (`open_`), and the history sees it only when
  `commit` pushes it (`command/executor.h`).
- **`rerunHead` and `revertHead` take records out of the history without undoing them** (`popHead`,
  `command/executor.cc:827` and `:881`).
- **`CommandExecutor::interactiveCommand()` is a pointer,** with nothing to tell one open command from the next.
- **`pickScene` answers for the last `evaluateScene`** (`scene/pick_scene.h`). `PickFilter::accept` restricts
  it to some objects, which a stroke's ray needs.
- **The test app's root has `scene` and `evaluated`** (`source/coredcc/testapp/host.cc`).
  `apps/testapp/src/gpu.ts` clears the canvas each frame and says the DrawList renderer replaces it.

## Key decisions
1. **A new module, `tool/`,** above `scene/`. `draw/` gets the DrawList and the OverlayDrawable capability,
   which need nothing of `scene/`.
2. **The DrawList is bytes:** a header, then 8-byte aligned records. Every 3D record is in floats relative to a
   double origin, or to a pushed double matrix. Hosts read it in one copy per frame.
3. **Gizmos edit objects only through `core.object.dragDelta`** (P3's ApplyDelta). P4 adds no transform math
   for objects. Element transforms get their own command with the same TransformDelta.
4. **Gizmos are a list, each with numbered parts,** not a tree of interfaces. A script can't return an interface
   or hold child interfaces, and every built-in gizmo is one handle with parts. This deviates from §11
   ("Gizmos form a tree").
5. **Modals are pushed, not returned.** A gizmo's `beginDrag` or a tool's `onEvent` begins the command and calls
   `ToolManager::pushModal`. The manager commits or cancels the command when the modal finishes.
6. **The manager notices a drag that was ended behind its back** (an undo during a drag, a host's cancel, a slot
   that committed it) by checking that its modal's command is still the open one: before each event and draw, and
   after every slot call. The executor gets an `interactiveSerial()` for that, moved by every begin, commit and
   cancel.
7. **A tool's event slots run as the script's top level.** The gate table in `bind/` lets `Tool.onEvent`,
   `Modal.onEvent` and `Gizmo.beginDrag` call what a script's top level may call, and `runCommand` runs a
   top-level command there. Draw, hit-test and placement slots may only read, and the reads of scenes are
   allowed there (each facade is marked as a read or a write).
8. **Hover is a move that `onEvent` gets.** Tools have no separate `hover` slot (a deviation from §11).
9. **Tool settings are a Runtime extension like LastUsedStore,** by path `toolSettings["core.tool.transform"]`,
   not undoable, with `serialize` and `load`.
10. **The Unreal spike builds coredcc with UE's flags** and tests `UnrealHistory` and the ITF adapter as UE
    automation tests in a headless editor. It lives in `apps/unreal-spike/`, outside the gates and CI.
11. **Errors from slots are taken right after each call.** A script's exception becomes the Runtime's sticky
    error and a default return (`base/iface/iface.h`), so the manager calls `takeStickyError()` after every slot
    call. An error in an event slot cancels the modal; an error in a draw slot is reported and keeps the drag.
12. **Scripts pass geometry as flat arrays of numbers.** litestl's TS runtime writes spans and Vectors element by
    element as numbers only, so the bound forms of the DrawList's appends and of per-object deltas take
    `Vector<double>`.

## DrawList (`draw/drawlist.h`, `draw/drawlist.cc`)
```cpp
enum class DrawKind : uint16_t { Lines = 1, Points = 2, Triangles = 3, Shape = 4, Circle2D = 5,
                                 Line2D = 6, PushMatrix = 7, PopMatrix = 8 };
enum class DepthMode : uint8_t { Test = 0, Always = 1, XRay = 2 };
enum class ShapeKind : uint16_t { Arrow = 1, Cone = 2, Cube = 3, Sphere = 4, Disc = 5, Ring = 6, Quad = 7 };

/** What every record has besides its geometry. */
struct DrawStyle {
  uint32_t color = 0xffffffff;  // RGBA8, straight alpha, R in the lowest byte
  float width = 1.0f;           // lines and outlines: logical pixels; points: diameter
  DepthMode depth = DepthMode::Test;
  uint32_t id = 0;              // the gizmo part or element it draws; 0 for none
};

class DrawList {
public:
  void begin(const double3 &origin);   // empties it; the matrix stack is empty
  void end();                          // frozen until the next begin
  bool frozen() const;
  const double3 &origin() const;

  /* 3D, in the space of the innermost PushMatrix, or the world. */
  Status lines(const DrawStyle &, std::span<const double3> pairs);
  Status points(const DrawStyle &, std::span<const double3> points);
  Status triangles(const DrawStyle &, std::span<const double3> corners,
                   std::span<const uint32_t> colors = {});   // one per corner, or none
  Status shape(const DrawStyle &, ShapeKind, const mat4d &matrix);
  Status pushMatrix(const mat4d &m);   // current = current · m
  Status popMatrix();

  /* 2D, in device pixels of the View's space, y down. */
  Status circle2d(const DrawStyle &, double x, double y, double radius, bool filled);
  Status line2d(const DrawStyle &, std::span<const double> xy);

  std::span<const uint8_t> bytes() const;   // valid until the next begin
  /* Bound for scripts: the same appends with flat numbers (xyz, xyz, ...; xy, ...), since litestl's TS
   * runtime can't write a span of structs. begin and end aren't bound: the manager owns the frame's list. */
  Status linesXyz(const DrawStyle &, const litestl::util::Vector<double> &xyz);   // and points, triangles, line2d
  /* For scripts: the bytes' address in the module's memory (WASM only), their size, and a copy. */
  int64_t address() const;
  int64_t size() const;
  Status read(int64_t offset, std::span<uint8_t> out) const;
};

/** Walks a list's records and checks them: sizes, alignment, counts, kinds, balanced pushes. */
class DrawListReader { ... };
```
- **Layout** (in `docs/drawlist-format.md`, version 1):
  - Header, 48 bytes: magic `CDDL`, version (u16), flags (u16), record count (u32), byte size (u32), padding,
    origin (3 doubles).
  - Record header, 8 bytes: kind (u16), depth (u8), flags (u8), byte size of the whole record (u32), a multiple
    of 8. Then color (u32), width (f32), id (u32), and the kind's payload, padded to 8.
  - Lines, Points, Triangles: a vertex count, then 3 floats per vertex; Triangles may have a color per corner.
  - Shape: the kind (u16) and a column-major matrix of 16 doubles. The shapes' geometry is defined in the
    document (an arrow is a shaft from 0 to 0.8 and a cone from 0.8 to 1 along +z, and so on), so hosts draw
    the same thing and the gizmos' hit tests match it.
  - PushMatrix: 16 doubles. PopMatrix: nothing.
  - Circle2D and Line2D: floats.
- **Precision.** With an empty stack, a 3D point is stored as `float(p - origin)`. Under a PushMatrix it is
  stored as `float(p)` in that space. The outermost PushMatrix's translation is stored minus the origin, in
  double. So an object at 1e9 drawn in its own space keeps its float geometry's precision. The tools set the
  origin to the camera's position.
- **The `id` of a gizmo's records** is the gizmo's id in the manager times 65,536 plus the part, so parts of two
  gizmos don't collide, and a test or host can tell which part a record draws.
- **Errors, not aborts:** a non-finite number, an append after `end`, a pop without a push, a record over
  2³¹ bytes or a list over 2³² - 1 bytes is InvalidArgument and appends nothing. (A limit on the vertex count
  alone would let a record's u32 byte size overflow first.) `end` with pushes left is InvalidArgument, and pops them.
- **Lifetime** (§10): frozen between `end` and `begin`; hosts take the bytes again each frame and never keep a
  typed-array view.
- **For scripts:** `address()` and `size()` give a zero-copy view of WASM memory, taken again each frame.
  `read` copies in parts, for N-API, where memory isn't shared (the 64 KB parts that `bytesRead` uses).
- **Unreal:** Lines and Points map to PDI's `DrawLine`/`DrawPoint` (XRay in two passes, §10), Triangles and
  Shapes to `FDynamicMeshBuilder`, and 2D records to `FCanvas` in `DrawHUD`. The spike checks the mapping.

## Tools, modals and the manager (`tool/tool.h`, `tool/manager.h`)
```cpp
enum class EventResult : int32_t { Unhandled = 0, Handled = 1 };
enum class ModalResult : int32_t { Continue, PassThrough, Finish, Cancel };

struct Tool : IfaceRef {        // the persistent, user-selected tool; one instance per activation
  Status activate(Context &ctx, ToolManager &tm);           // adds its gizmos
  void deactivate(Context &ctx, ToolManager &tm);
  EventResult onEvent(Context &ctx, ToolManager &tm, const ViewMath &view, const InputEvent &e);
  void drawOverlay(const ViewMath &view, DrawList &out) const;           // optional
};
struct Modal : IfaceRef {       // one gesture's grab
  ModalResult onEvent(Context &ctx, ToolManager &tm, const ViewMath &view, const InputEvent &e);
  void drawOverlay(const ViewMath &view, DrawList &out) const;           // optional
  void end(Context &ctx, bool committed);                                // optional
};
struct GizmoHit { int32_t part = -1; double distance = 0; double depth = 0; };
struct Gizmo : IfaceRef {
  void update(Context &ctx);    // follows the document: pivot, orientation, visibility
  GizmoHit hitTest(const ViewMath &view, double x, double y) const;
  void draw(const ViewMath &view, int32_t hoverPart, int32_t activePart, DrawList &out) const;
  Status beginDrag(Context &ctx, ToolManager &tm, const ViewMath &view, const InputEvent &e, int32_t part);
};

class ToolDef {                 // like CommandDef: id, uiName, icon, settings, a layout, a factory
  ToolDef &setting(PropertyDef def);
  ToolDef &layout(std::string_view xml);   // its options panel; paths are relative to its settings
};
class ToolRegistry;             // a Runtime extension; a duplicate id is AlreadyExists

class ToolManager {
public:
  explicit ToolManager(Runtime &rt);
  ~ToolManager();               // drops modals and the tool without running anything; call shutdown first
  Status setActive(Context &ctx, std::string_view toolId);
  const ToolDef *active() const;
  Result<EventResult> dispatch(Context &ctx, const View &view, const InputEvent &e);
  Status draw(Context &ctx, const View &view, DrawList &out);   // begin, scene overlays, tool, gizmos, modal, end
  Status cancel(Context &ctx);  // ends a modal, cancelling its command
  void shutdown(Context &ctx);

  /* For tools and gizmos. */
  Status pushModal(Context &ctx, Owned<Modal> modal, bool ownsInteractive);
  bool modalOpen() const;
  int32_t addGizmo(Owned<Gizmo> g);
  void removeGizmo(int32_t id);
  const litestl::util::string &status() const;    // for the host's status bar
  void setStatus(std::string_view text);
  double hitRadius = 6.0;       // logical pixels
};
```
- **Dispatch order** (§11):
  1. The top modal. `PassThrough` returns Unhandled (a wheel zoom during a drag). `Finish` commits its command
     if it owns one, `Cancel` cancels it; both pop the modal and call its `end`.
  2. On a press, the gizmo part under the cursor: every gizmo's `hitTest`, ranked by distance and then depth,
     within `hitRadius`. Its `beginDrag` should push a modal.
  3. The active tool's `onEvent`.
  4. Otherwise Unhandled, for the host.
- **Hover:** on a move without a modal, the hovered part is found again, and gizmos draw it highlighted. The
  move also goes to the tool.
- **A modal that owns the interactive command** records `executor.interactiveSerial()` when it is pushed. The
  serial moves with every `beginInteractive`, `commit` and `cancel`, so an undo that only cancels moves it too.
  Before each event and draw, and after every slot call, the manager walks the whole modal stack: a modal that
  owns a command is still valid only if `interactiveOpen()` and the serial is its own. One that isn't (an undo
  cancelled it, the host did, or a slot committed or cancelled it itself) is popped, with the modals above it,
  with `end(ctx, false)`, and the executor isn't called for it.
- **The manager acts on the modal it called,** not on the top of the stack. Suppose A's `onEvent` pushes B and
  returns Finish. Popping "the top" would pop B and commit A's command. Instead, a modal that returns Finish or Cancel
  while modals are above it is an error (InvalidArgument): the modals above it are cancelled first, then A is
  cancelled.
- **`pushModal(..., ownsInteractive=true)` with no open command,** or with one that another modal owns, is
  FailedPrecondition. A slot that begins an interactive command and pushes no modal is caught after the slot
  returns: the manager cancels the command and reports FailedPrecondition.
- **Cancel and FocusLost** go to the modal. If it returns anything but Cancel, the manager cancels it anyway.
  `ToolManager::cancel` does the same for the host.
- **Gizmos removed during a dispatch** (by a tool's or a gizmo's slot) are removed when the dispatch ends, so no
  slot runs on a freed gizmo.
- **Settings:** when the active tool's settings change (the store notifies the manager), its optional
  `settingsChanged(ctx, tm)` slot is called at the next dispatch or draw, so the transform tool can swap its
  gizmo when `mode` changes.
- **Script tool instances** are counted in `ForeignBindings` as script command instances are, so a manager that
  outlives the Runtime is caught at teardown.
- **Busy:** `setActive` while a modal is open or during a dispatch; `dispatch` and `draw` inside a dispatch
  (a tool that dispatches from its slot); everything while a graph evaluates.
- **Errors:** a script's exception doesn't come back as a Status: the forwarder sets the sticky error and returns
  `R()` (ok, Unhandled, Continue, part -1). So the manager takes the sticky error after every slot call:
  - in `onEvent`, `beginDrag`, `activate`: the modal is cancelled (a failed `activate` leaves no tool active), and
    `dispatch` or `setActive` returns the error;
  - in `drawOverlay`, `draw`, `hitTest`, `update`: `draw` or `dispatch` returns it after finishing, and the drag goes on,
    so that one bad frame doesn't make `commit` find a pending error and cancel the drag.
  A gizmo whose `beginDrag` pushed nothing and returned ok leaves the event Handled.
- **A click on a gizmo without a move** makes no undo step: the gizmo's modal sees that ApplyDelta has nothing
  `changed`, and cancels (P3's contract).
- **Lifetime:** like the executor, the manager is destroyed before the Runtime. A tool's instance lives from
  `activate` to `deactivate`.
- **The Context slot:** `ToolManager *tools() const` and `setTools(ToolManager *)`, as for the executor.
- **Settings:** `ToolSettingsStore` (a Runtime extension, `tool/settings.h`), modelled on LastUsedStore: a
  keyed collection `toolSettings["<tool id>"]` added to a root struct with `addCollectionTo`; values coerced by
  the ToolDef's PropertyDefs; `serialize`/`load`; not undoable. A ToolDef's layout is validated against its
  settings struct when it is registered (`layout/validate.h`).

## Gizmos (`tool/gizmos/`)
- **Built-ins:** `core.gizmo.translate` (3 arrows, 3 planes, a view-plane square), `core.gizmo.rotate`
  (3 rings and a view ring), `core.gizmo.scale` (3 axes, 3 planes, a uniform centre).
- **Placement:** each `update` reads the selection's pivot and orientation from the last evaluation
  (`Scene::evaluated`): the median, the active object's, or each object's (INDIVIDUAL draws at the median).
  - The median is over the same objects that ApplyDelta moves: selected, visible and selectable, and not below another
    of them (`scene/apply_delta.cc:92-112`). Otherwise a parent at x = 0 with its child at x = 10 would draw the gizmo
    at 5 and rotate about 0. A test checks that the drawn pivot equals the median of `startPivot`.
  Reading the last evaluation is right for drawing; the drag itself starts from ApplyDelta's `startState` and
  `startPivot`, which are computed fresh (P3's rule 9).
- **Constant size on screen:** the scale is `ViewMath::pixelSizeAt(pivot) · size` logical pixels (the tool's
  `size` setting). Hit tests use the same parameters as drawing: an arrow is a segment and a cone, a ring is a
  circle, both scored by their distance in pixels.
- **Axes that face the eye are hidden** (an arrow within about 8° of the view direction, a plane within about
  8° of edge-on), and can't be hit. That is where the drag's math is ill-conditioned.
- **The drag's math** (`tool/gizmos/drag_math.{h,cc}`), in world space, from the press:
  - along an axis: the point of the axis nearest the pixel's ray, minus that point at the press;
  - in a plane, or the view plane: the ray's intersection with the plane, minus the press's;
  - rotation about an axis, or the view direction: the angle of the cursor about the pivot's projection,
    unwrapped across ±π so it accumulates (a 720° drag is 720°), with its sign from which way the axis faces;
  - scale: the ratio of the cursor's distance from the projected pivot to the press's, along the projected
    axis, or overall for the centre.
  - Each gives a `TransformDelta` with the gizmo's basis and pivot. Ctrl snaps the vector, angle or factor to
    the tool's steps. INDIVIDUAL and LOCAL give one delta per object (`ApplyDelta::update(span)`).
- **Status text:** "Move 1.25 m along X", in the scene's units (`Context::units()`), plus "2 objects locked" or
  "driven" from ApplyDelta's counts.

## The built-in tools (`tool/select_tool.cc`, `tool/transform_tool.cc`)

## Elements and symmetry (`tool/elements.h`, `tool/elements.cc`)
```cpp
/** What gather gives: the points that a transform of a domain's selection moves. */
class ElementSet {                     // a sink, as PickSink is
public:
  void add(int32_t handle, double x, double y, double z, double weight);   // the block's own space
};
struct TransformableElements : IfaceRef {   // the block also implements ElementAccess (topoStamp, positions)
  Status gather(int32_t domain, ElementSet &out) const;   // the selected elements of `domain`, as points
  Status setPositions(const litestl::util::Vector<int32_t> &handles,
                      const litestl::util::Vector<double> &positions);    // 3 numbers per handle
};
struct Symmetry : IfaceRef {
  uint32_t axes() const;               // bits 1, 2, 4: mirrored across the block's x, y, z = 0 planes
  litestl::util::Vector<int32_t> partners(const litestl::util::Vector<int32_t> &handles,
                                          int32_t axis) const;   // the mirror of each; itself on the plane; -1 none
};
```
- Both are block capabilities, found on the data block first (`objectQuery`). They are coredcc's own: faberforge's
  `ITransDataType` is the model for TransformableElements, but its undo and its update hooks aren't, because
  coredcc's command does the undo and `invalidateData` the update.
- **`core.elements.applyDelta` and `core.elements.dragDelta`** (Interactive) take the same TransformDelta inputs as
  P3's object commands, and work on the scene's selected objects whose data block has TransformableElements and a
  selection in `domain`.
  - Per object: `W = computeState(...).world` at the start (overrides included); a point moves to
    `W⁻¹ · D(w) · W · p`, where `D(w)` is the delta weighted: `w·v` for a translation, `w·angle` for a rotation, and
    `1 + w·(s - 1)` per axis for a scale. An object whose `W` has no inverse is skipped.
  - **Symmetry,** with the tool's `symmetry` on: for each non-empty set of the block's axes, the partner of each moved
    point that isn't moved itself gets the moved point's position mirrored. A point that is its own partner keeps
    its coordinate on each mirror plane at 0. Partners of several axes are found by asking one axis after the other.
    - **Conflicts:** an unselected point can be the partner of two moved ones. With x and y symmetry, P = (1, 1) and
      Q = (-1, 1) selected, S = (-1, -1) is P's partner across {x, y} and Q's across {y}. The source whose set of axes
      is smallest wins (Q here), then the one with the lower axis bits, then the lower handle. The order of `gather`
      doesn't matter.
  - **Undo** keeps, per block, the handles of every point it writes (partners included), their positions before and
    after, and the topoStamp. The partners' positions before come from `ElementAccess::positions`, since `gather`
    gives only the selected points. Undo and redo write with `setPositions` and call `invalidateData(Positions)`. A
    different topoStamp is FailedPrecondition, so the history drops the step (its rule for a failed undo) rather than
    writing positions to other points. A block without ElementAccess can't be transformed (skipped).
  - **`setPositions` may write the block's properties:** in scripts it is gated like a Command's `exec`, `undo` and
    `redo` (`writeValue` only), since the element command calls it in all three.
  - **Scripts** drive `core.elements.dragDelta` with `elementsDragUpdate(ctx, delta)`.
  - `memSize` is 52 bytes per point (handle, 6 doubles).
- **StrokeSampler** uses only `Symmetry::axes`.

## StrokeSampler and the stroke command (P4b; `tool/stroke.h`, `tool/stroke.cc`, `tool/stroke_curve.h`)
- **A generic port of sculptcore's `brush/stroke_driver`** (`stroke_driver.{h,cc}`, `stroke_curve.h`,
  `stroke_spacing.h`; 38 KB). It turns pointer samples into evenly spaced samples along a centripetal Catmull-Rom
  spline, in screen or world spacing, all in double.
- **What changes in the port:**
  - The view is a coredcc `ViewMath`, not its own `StrokeView` with row-vector matrices.
  - The ray goes to `pickScene` with `PickFilter::accept` limited to the target object, not a sculptcore
    `SpatialTree`. A miss is synthesized on the plane through the last hit, as the original does.
  - Brush fields (color, invert, the alternative brush, live radius and angle of the anchored method) are left out.
    The methods are PATH and DRAG_DOT; ANCHORED reports the anchor and the cursor and nothing brush-specific.
- ```cpp
  struct StrokeSample { double x, y; double3 world, normal; bool hit; double pressure, tiltX, tiltY, twist;
                        double radiusWorld, radiusPixels, distance, step, angle, time; uint32_t mirror; };
  class StrokeSampler {
    Status configure(const StrokeSettings &);   // space, method, spacing, radius, target object
    void setView(const ViewMath &);
    void push(const PointerSample &);
    void end();
    int32_t poll();                             // how many samples are ready
    const StrokeSample &sample(int32_t i) const;
    bool finished() const;
  };
  struct StrokeBrush : IfaceRef {               // what a client's brush implements
    Status begin(Context &ctx);
    Status apply(Context &ctx, const StrokeSample &s);
    void undo(Context &ctx);
    uint64_t memSize() const;
  };
  ```
- **`core.stroke` (Interactive)** forwards to a StrokeBrush that the tool names, and **records every sample** it
  applied.
  - **The record owns the brush** (an `Owned<StrokeBrush>`; for a script brush, a kept handle), so undo and redo work
    after the tool is deactivated. `memSize` is the brush's plus the samples' (about 160 bytes each).
  - `apply` runs inside `updateInteractive`, where sub-commands are refused, so a script brush may only `writeValue`
    there, as a Command's `undo` may. Its `redo` calls `begin` and `apply` with the recorded samples again, which is the architecture's
  "a stroke command can override `redo` by replaying them". With the block's Symmetry axes it applies each sample
  once per mirror, reflected in the object's space, with `mirror` set to the axes.
- **`core.tool.stroke`** connects them: a press begins `core.stroke`, moves push the event's coalesced samples, and a
  release ends the sampler and commits.

## The Unreal spike (`apps/unreal-spike/`)
**What it must prove:** that `UnrealHistory` (P6) can put coredcc's commands into Unreal's undo, and that one ITF tool
can host coredcc's tools, gizmos and DrawList.

**How:**
- `tools/unreal-spike.mjs` builds and runs it:
  1. builds coredcc as a subproject (not top-level) with UE's flags: `/EHsc /GR- /MD`, RelWithDebInfo without
     iterator debugging, at 2 jobs, into `build/unreal-spike/`;
  2. builds the project's Editor module with UBT (`-MaxParallelActions=2`);
  3. runs `UnrealEditor-Cmd.exe` headless with `-ExecCmds="Automation RunTests Coredcc;Quit" -unattended -nullrhi`;
  4. reads the log and writes `build/unreal-spike/report.txt`.
- The project: one Editor module with `UnrealHistory.{h,cpp}`, `CoredccToolAdapter.{h,cpp}` (one `UInteractiveTool`
  and its builder), `DrawListPdi.{h,cpp}`, `ViewFromSceneView.{h,cpp}` and automation tests. No assets.
- **`UnrealHistory`** implements coredcc's `UndoHistory`:
  - `push` opens an `FScopedTransaction` named by the command's uiName and stores an `FCommandChange` holding the
    record (`StoreUndo` on a transactional `UCoredccDocument` UObject, one per Library: FChange needs a UObject).
    `Apply` redoes the record, `Revert` undoes it, `GetSize` is `memSize`, and the destructor discards it.
  - `undo` and `redo` are `GEditor->UndoTransaction` and `RedoTransaction`; `canUndo` is `Trans->CanUndo`.
  - Folding: if the last transaction in the buffer is still this history's last change, and nothing was undone since,
    the next record is folded into the change it holds.
  - `head()` is null unless UE's newest transaction is this history's last change and nothing was undone since
    (`GetUndoCount() == 0`). rerunHead and revertHead depend on that, as folding does.
  - `popHead`: the change gives up its record and reports `HasExpired()`. UE skips expired changes and transactions
    when it undoes and redoes (`EditorTransaction.cpp:318`, `:541`, `:1636-1667`). It does **not** call `Trans->Undo`,
    which would undo whatever is on top (a UE edit after S3's interleaving), do nothing while a transaction is open,
    and broadcast as if the user had pressed Undo.
  - **An undo from Unreal while a coredcc drag is open:**
    - With the ITF adapter, the drag holds a UE transaction open, and `UTransBuffer::CanUndo` is false while one is
      (`EditorTransaction.cpp:1465-1474`). So Ctrl+Z does nothing during a drag. That matches coredcc's rule closely
      enough: coredcc's undo during a drag only cancels it (`executor.h`).
    - Without the adapter (a drag begun some other way), UE may undo one of its own transactions during the drag, and
      no coredcc `Revert` runs. UnrealHistory subscribes to `Trans->OnBeforeRedoUndo()` (`TransBuffer.h:202`) and
      cancels the open drag there. UE then also undoes its step, which coredcc's own history wouldn't; the spike
      records this difference.
  - **Context and errors:** each change keeps the Context its record ran in. `Apply` and `Revert` take the sticky
    error themselves and log it. LinearHistory's rule that a failed undo drops that step and everything after it
    can't be mirrored in UE's buffer: the step is expired instead, and the report says what follows.
  - **Teardown:** UE may destroy transactions after the Runtime is gone (module shutdown, hot reload). Before the
    Runtime goes, UnrealHistory expires every change it made and releases its record, and doesn't call `Trans->Reset`.
  - The `UCoredccDocument` anchor is rooted (`AddToRoot`) and transactional, or UE skips its records when it loads.
- **The ITF adapter:** input behaviors (click-drag, hover, keys) turn into InputEvents for a ToolManager; the adapter
  opens a UE transaction when a modal that owns a command begins and closes it at the end, so other UE edits during
  the drag join it; `Render` executes the DrawList through the PDI, `DrawHUD` its 2D records; `ViewFromSceneView`
  copies the FSceneView's matrices (the 16 numbers, as measured above) and conventions.

**Tests (automation, headless):**
- S1: the module links coredcc and litestl and loads; a Runtime is made and destroyed; litestl's alloc tracker reports
  no leaks.
- S2: `core.scene.new`, `core.object.add` and `core.object.applyDelta` through an executor with UnrealHistory: one
  transaction each, named; `UndoTransaction` reverts the location; `RedoTransaction` redoes it; coredcc's
  `executor.undo` does the same.
- S3: a UE property change on a transactional UObject between two coredcc commands; three undos and three redos in
  order.
- S4: two nudges of one gesture fold into one transaction.
- S5: a drag (begin, ten updates, commit) is one transaction; a cancelled drag is none and restores the channels.
  An Unreal undo during an open drag, in both configurations: with the adapter's open transaction it is refused and
  the drag goes on; without it, `OnBeforeRedoUndo` cancels the drag first, and the channels are as before the drag.
- S6: `Trans->Reset()` and a truncated redo call each record's `discard` exactly once; the transaction buffer's size
  includes `memSize`.
- S7: `rerunHead` through `popHead`, also after a UE edit was made on top (head() must then be null, and rerunHead
  refused).
- S8: the ITF adapter in a `UInteractiveToolsContext` made by the test, with a transactions API that forwards to
  GEditor: a press, drag and release on the X arrow's pixel moves the object, makes one transaction, and undo puts it
  back. A recording `FPrimitiveDrawInterface` counts the lines, points and meshes that `Render` emits, against the
  DrawList's records.
- S9: a View from a real `FSceneView` (its `UnscaledViewRect`, and `GetProjectionNoAAMatrix()` so TAA's jitter is
  left out) validates. `ViewMath::project` of three points matches a double reimplementation of
  `FSceneView::WorldToPixel` within 1e-6 pixels, and UE's own within 1e-3 (UE computes `InvW` and `Y` in float,
  `SceneView.cpp:1442-1446`, about 1e-4 px at 1280 wide).
- S10: a block type over an `AActor` (Transformable writing the actor's transform without `Modify`, then
  `MarkPackageDirty`): a coredcc drag and its Unreal undo restore the actor; UE's own transaction doesn't record the

- S11: coredcc's and litestl's public headers compile inside a UE translation unit with its flags, including
  `/we4668`, the shadowing errors, `/Zc:strictStrings-` and `/D_DISABLE_EXTENDED_ALIGNED_STORAGE` (`compile_embed`

**Exit criteria:**
- **Feasible (P6 writes UnrealHistory):** S1 to S6, S8, S9 and S11 pass. S7 and S10 may fail with their limits written
  down (no last-command panel in Unreal; host objects need another rule).
- **Not feasible:** S2 to S5 fail for a reason that can't be fixed in the adapter. The report then says what P6 does

## What was built differently
Kept up to date as the work goes; each item says why.

### Step 1: DrawList (commit after `600497e`)
- **The record header is 24 bytes,** not 8 bytes followed by the style: kind, depth, flags, size, color, width, id
  and an `aux` word, which is the vertex count of Lines, Points, Triangles and Line2D and the shape of a Shape. So
  every payload starts at offset 24 and no kind has its own count field. `docs/drawlist-format.md` is the format.
- **The header** is magic, version, flags, record count, byte size, then the origin at offset 16 and a reserved
  u64 at 40 (48 bytes, as planned; the padding moved to the end so the doubles are aligned).
- **`DepthMode` and `ShapeKind` are `int32_t` enums** in C++, so they bind as numbers; the bytes still hold a u8 and
  the aux word.
- **`begin` and `end` return Status.** `begin` empties the list whether or not it is frozen, and refuses an origin
  that isn't finite (it uses 0 then). `end` with pushes left pops them and returns InvalidArgument, as planned.
- **OverlayDrawable has no `OverlayContext`:** the slot is `drawOverlay(const ViewMath &view, uint32_t state,
  DrawList &out)`, with `OverlayState` bits for `state`. A struct of pointers is awkward to bind, and nothing needed
  the time. `tool::drawSceneOverlays` comes with step 3, with the scene dependency.

### Step 2: the tool core
- **Results are numbers:** `eventresult::kUnhandled/kHandled` and `modalresult::kContinue/kPassThrough/kFinish/
  kCancel` are `int32_t` constants, and so are `modifiers::k*` and `keys::k*`, not enum classes. A foreign slot's
  return comes back as a number, and a script's exception returns `R()`, which is 0: Unhandled and Continue, as
  planned.
- **`Gizmo::draw` takes `idBase`** (the gizmo's id × 65,536), so a gizmo doesn't need to know its id.
- **The manager exposes more,** for hosts and tests: `hoverGizmo/hoverPart`, `activeGizmo/activePart`,
  `modalCount`, `gizmoCount`, `clearGizmos`, `runtime`, `kIdStride`.
- **`manager.h` doesn't include `tool.h`;** `tool.h` includes `manager.h`. The interfaces' slots take
  `ToolManager &`, and binding them needs ToolManager complete, so the manager keeps its tool, modals and gizmos
  behind structs defined in `manager.cc`.
- **Settings changes are polled:** ToolSettingsStore keeps a version per tool, and the manager compares it before
  each dispatch and draw, instead of the store notifying the manager. Same effect, and the store needs no list of
  managers.
- **`ToolRegistry::check` is `validateDef`:** `compile_embed` defines Unreal's `check` macro, which broke the name.
- **A ToolDef's layout is checked** against a struct of its settings registered under a name of its own
  (`ToolSettingsCheck:<id>#<n>`) before the def is registered, since the real settings struct needs the def.
- **Not yet:** counting script tool instances in `ForeignBindings`, and `runCommand`, come with the bindings
  (step 5).

### Step 3: gizmos, the transform and select tools
- **One gizmo for the three modes:** `tool/gizmos/transform_gizmo.cc` (geometry, hit tests, drawing, `beginDrag`)
  and `transform_modal.cc` (the drag), not `translate.cc`, `rotate.cc` and `scale.cc`. The modes share the frame
  (`Frame`: pivot, axes, size, what is hidden), and a part's hit test and drawing read the same `Frame`.
- **During a gesture gizmos aren't updated,** and the dragged gizmo draws nothing: its modal draws the dragged part
  where it is now, and the other parts are hidden, as in Blender. Placing a gizmo reads the whole selection, which
  is O(selection) per frame; a drag doesn't pay it on each move.
- **The median pivot is the mean** of the objects' positions, as Blender's "median point" is.
- **Blender's look** (decision 4): size 75 logical pixels; axis colors #ff3352, #8bdc00, #2890ff; alpha 0.6,
  1.0 under the cursor; an axis fades out as 1 - |cos| goes from 0.1 to 0.02 and a plane as |cos| goes from 0.25
  to 0.175 (`g_tw_axis_range` in Blender's `transform_gizmo_3d.cc`). Rings are drawn and hit on their front half.
- **The sign of a turn** comes from the screen's handedness at the pivot (`screenHandedness`), so mirrored views and
  left-handed worlds turn the right way. The drag math test checks it only where the whole ring is in front of the
  eye: a ring that passes behind the eye projects to no closed curve, and has no orientation on the screen.
- **Translate and rotate deltas are in the world** (identity basis); scale's are in the gizmo's basis.
  INDIVIDUAL and LOCAL give each object its own delta from `startPivot` and `startState`.
- **The status text has no units yet** ("Move 1.25 along X"): `Context::units()` formatting comes with the
  documents step, if at all. It names locked and driven objects as planned.
- **A click doesn't make the clicked object active:** core.scene.select has no active input, and running
  core.scene.setActive too would make two undo steps of one click (decision 1).
- **The status text is emptied when a gesture ends.**
- **ToolManager::draw draws the scene's overlays** (`tool/scene_overlay.cc`, `drawSceneOverlays`) first, then the
  tool's, the gizmos' and the modals'.
- **The test fixture** (`tests/tool/tool_fixture.h`) builds on `scene_test::CommandDoc` and its `test.Shape` data
  blocks (bounds and Spatial), instead of a `box_block.h` of its own. `tests/tool/view_cases.h` is a copy of P3's
  view generator, so P3's test stays as it is.
- **Measured** (`bench_tool_drag`, clang RelWithDebInfo, ms per move): 1 object 0.002 (target 0.2); 1,000: 0.774,
  of which ApplyDelta 0.761; 100,000: 117.4, of which ApplyDelta 116.6, so the manager and gizmo add 0.8 (target 1).
  With the evaluate and draw of a frame: 0.004, 0.978 and 145.5.
- **Drag math precision** (`test_tool_drag_math`, all 48 conventions): the worst error relative to the move is
  2.4e-13 at offset 0, 6.8e-12 at 1e3, 7.0e-9 at 1e6 and 3.6e-6 at 1e9.

### Step 4: elements and symmetry
- **ElementSet** keeps its handles, positions and weights in public vectors; scripts see only `add` and `size`.
- **Objects that share a data block** move its points once (the first object's matrix is used).
- **Each `update` writes every point it owns** (moved and partners) with one `setPositions`, and posts
  `invalidateData(Positions)`; the topoStamp is checked before every write, not only before undo and redo.
- **Elements have no INDIVIDUAL pivot or LOCAL basis of their own:** the gizmo's delta applies to all points, in the
  world. The gizmo's pivot for ELEMENTS is the mean of the gathered points in the world, gathered on every frame
  outside a gesture (O(selected points)).
- **The transform tool's settings** gained `target` (OBJECTS, ELEMENTS), `domain` and `symmetry`.
- **Outputs** are `skipped` (objects without elements in the domain) and `points` (points moved, partners not
  counted).
- `elementsDragUpdate` for scripts comes with the bindings (step 5).

### Step 5: bindings and TS
- **The gate table is in `slotGate` itself, by name,** not in a table in `bind/`: `bind/` can't depend on `tool/`'s
  descriptors from the gate's callers, and `inForeignSlot` already matches by name. `Tool.settingsChanged` is an event
  slot too (it may add and remove gizmos).
- **`Gate::Read`** (a fourth argument) is allowed in every slot but a graph kernel's and a transform model's. The reads
  of `scene_facades.cc` pass it, so a script command's `canRun` may now read them as well;
  `test_bind_scene`'s expectation changed with it.
- **`TransformableElements.setPositions` passes the gate of a Command's `undo`** (what `writeValue` allows).
- **`StrokeBrush` gates come with step 7.**
- **`toolRemoveGizmo` is a Read,** so `deactivate` and `end` may remove gizmos.
- **`dragUpdateEach` takes 16 numbers per object,** not 18: the plan's own list (kind, basis, pivot, vector, axis,
  angle, a spare) is 16.
- **`dragCount(ctx)`** was added: a script needs it for `dragUpdateEach`.
- **`drawListRead(list, offset, out)`** is the copy for hosts that can't view the module's memory. `DrawList::read` takes
  a span, which a bound method can't.
- **The test app's host owns a ToolManager** and registers the built-in tools.
- **TS:** `defineTool`, `pushModal`, `addGizmo` (`'transform'` or a script gizmo), `removeGizmo`, `dragUpdate`,
  `dragUpdateEach`, `elementsDragUpdate`, `dragCount`; `setActiveTool`, `activeTool`, `sendEvent`, `drawTools`,
  `cancelTool`, `toolStatus` and `setToolStatus` for hosts; and `Drawer`, `readDrawList` and `decodeDrawList`.
  - `tool.ts` keeps a copy of `scene.ts`'s private `withView`, since `scene.ts` is P5c's to edit.
  - `core.ts` gained `moduleHeap()` for the zero-copy view.

### Step 6: TA3
- **The renderer tessellates on the CPU,** not in a vertex shader: lines, points and the 2D records become clip-space
  quads in JS numbers, so one shader and three pipelines (Test, Always, and X-ray's hidden pass at a third of the
  alpha) draw everything. The origin is taken out of the view-projection in double, as the format asks.
- **`shot()` can't check the overlay.** A hidden NW.js window doesn't composite frames drawn outside rAF (and rAF
  doesn't run there), so `capturePage` returns an old frame. The test reads the pixel back from the GPU instead
  (`pixel(x, y)`, `copyTextureToBuffer` of the canvas texture, configured with COPY_SRC).
- **`frame()` throws WebGPU's validation error,** taken with an error scope, rather than leaving a stale canvas.
- **`input` takes events only,** not event scripts: `parseEventScript` isn't bound.
- **More testbus methods than planned:** `scene('gizmo')`, `worldMatrix(ref)` and `pixel(x, y)`; `view()` also gives the
  canvas's place in the page.
- **`testapp.Box`** (`source/coredcc/testapp/boxes.*`): Spatial and OverlayDrawable on one struct over the Box data;
  `testapp::addBox(host, half)` makes one for `core.object.add`'s `data`. The root struct gained `toolSettings`.
- **`gpu.ts`** gained `gpuState`, `setRenderer`, `renderNow` and `readPixel`, which `main.ts` hands the backend bundle
  (a separate bundle, so it can't import them).

### U-A: the Unreal spike, history half (2026-11-26)
**Result: S1 to S7, S10 and S11 pass** (`node tools/unreal-spike.mjs`, `build/unreal-spike/report.txt`). For P6,
UnrealHistory is feasible as planned.
- **Toolchain:** UBT used MSVC 14.52.37029 and SDK 10.0.26100, with the "not a preferred version" warning. Nothing
  failed because of 14.52, so 14.50 wasn't needed.
- **Times:** coredcc with Unreal's flags, from cold, a few minutes at 2 jobs (2 s when nothing changed). The Editor
  module: about 70 s from cold, then 20 s. The headless test run: 61 s the first time, 17 s after.
- **What the spike found in coredcc and litestl:**
  - **`InputEvent` had a zero-size array:** `Vector<PointerSample, 0>` makes litestl's inline storage `uint8_t[0]`,
    an MSVC extension. With Unreal's flags MSVC refuses a `std::span<const InputEvent>` (C2233). Now
    `Vector<PointerSample, 1>` (in this branch's `tool/input.h`).
  - **S11 needs two warnings off around coredcc's includes:**
    - C4458 in `litestl/binding/binding_struct.h`: `Struct::add`'s `name` and `type` hide members. To fix in litestl,
      by a PR from the submodule.
    - C4668 in Eigen (through `litestl/math/matrix.h`), which tests GCC's macros in `#if`. UE wraps its own
      third-party headers the same way (`THIRD_PARTY_INCLUDES_START`).
    - The spike puts its coredcc includes between `CoredccIncludesBegin.h` and `CoredccIncludesEnd.h`
      (`Private/CoredccIncludes.h` says why). U-B also made C4668 a warning for the whole module (see U-B).
    - litestl's binding headers also give C5038 (initialization order). That is a warning in UE, not an error.
  - **Include roots:** a host needs `source/`, `extern/`, `extern/litestl/` and `extern/litestl/extern/` (Eigen).
- **How UnrealHistory behaves:**
  - A command's transaction is named by its uiName ("New Scene", "Add Object", "Transform").
  - A gesture's sets fold into one transaction. After an undo and redo nothing folds, because UE's buffer can't
    tell coredcc that the head was touched; UnrealHistory keeps its own flag for that.
  - During a drag, the ITF adapter's open transaction makes `CanUndo` false and the drag goes on. Without the
    adapter, `OnBeforeRedoUndo` cancels the drag, and then UE undoes its own last step too. coredcc's own history
    wouldn't undo that step; this is the expected difference.
  - `Trans->Reset` and a truncated redo destroy the changes, and each record is discarded exactly once.
    `GetUndoSize` counts `memSize`.
  - `rerunHead` works through `popHead`: the old transaction's change expires, and UE skips it. After a UE edit on
    top, `head()` is null and `rerunHead` is refused.
  - **S10:** an AActor's location as a coredcc object. Writing it without `Modify` and marking the package dirty
    gives one transaction that doesn't record the actor, and UE's undo and redo move the actor through coredcc's
    record. Only the location is mapped.
- **Not tested here:** what a failed undo does in UE's buffer. The change expires and the error is logged; nothing
  produced a failure.

    so for a view a test or a tool builds. The compute form takes the jitter out of the live projection, and it works
    either way.
  - **C4668 is a warning for the whole module** (`CppCompileWarningSettings.UndefinedIdentifierWarningLevel`):

    - It didn't break anything else, because `#pragma once` and namespaces keep the two sets of headers apart.

- **P5c's promises** cover everything in "What P4 needs from P5c". Its Part B makes a drag's evaluation cheaper (at most

- No conflict remains.

## Pressure test record (2026-11-25)
A fresh agent was given this plan's first draft and the code, without the author's reasoning. It read the cited code,
litestl's foreign dispatch (TS and N-API) and UE 5.9's engine sources, ran one native experiment
(`pt-p4\drag_prec.cc`: the drag's precision with a real ViewMath at large offsets), and ran the author's UE view
prototype again. The author checked the two findings that changed the most (litestl's `writeScalar`, UE's `CanUndo`)
against the code.

### Survived
- The code facts and line references: `slotGate` (`bind/facades.cc:83`), `runCommand`'s use of `inForeignCall`,
  `popHead` (`executor.cc:827`, `:881`), `interactiveCommand()` as a bare pointer, the Context's slots.
- Scripts can't update a drag today; `writeInteractive` writes a path that ApplyDelta's undo doesn't take back.
- Scripts can't return an interface (`bind/foreign_command.cc:195-234`), so decisions 4 and 5 stand.
- The slots' argument shapes work through foreign dispatch: `Context&`, an opaque `ToolManager&`, `const ViewMath&`,
  `DrawList&` and `ElementSet&` arrive as scoped wrappers; `const Vector<int32_t>&` arrives as an array; a scalar
  Vector return works. A `GizmoHit` return needs a bound copy constructor and a converter, as `Status` has.
- ApplyDelta gives the gizmos what they need. A click makes no change. Euler angles stay continuous, so a 720° drag
  works when it is updated each frame. Cancel, undo and redo restore channels bitwise.
- `evaluateScene` and `pickScene` don't check for an open interactive command; only the Library's no-collect is in
  effect during a drag.
- Destroying the executor cancels an open command through its Context.
- LastUsedStore's members are NoUndo, the model for tool settings; `validateLayout` exists.
- The UE facts: the flags, `FChange`'s API, `DataSize` reading `GetSize()` live, ITF's API, the toolchain rules. The UE
  matrices copy as stated (the prototype's results reproduced).
- A subproject build of coredcc skips `coredcc_disable_exceptions_and_rtti`, so the spike can build with UE's flags.

### Broke, and what changed (most severe first)
1. **Scripts can't pass a span or Vector of structs.** litestl's TS runtime writes them element by element as numbers
   and throws for anything else (`binding.ts:326-387`, `:455-499`), and `double3` is a Struct. So a TS overlay couldn't
   call `lines(style, [[0,0,0], ...])`, nor `dragUpdateEach` with TransformDeltas.
   - Changed: the bound appends take a flat `Vector<double>` (decision 12); `dragUpdateEach` takes 18 numbers per
     object. No litestl PR.
2. **`slotGate` can't tell reads from writes,** and the scene's read facades gate to `exec`. A script gizmo couldn't
   place itself.
   - Changed: a Read/Write kind for `slotGate`, passed at five call sites in `bind/scene_facades.cc`. That file is now
     in "P4 changes in files that others own".
3. **A script slot's exception comes back as a default value and a sticky error,** not a Status (`iface.h:58-66`,
   `:230-246`). A throwing overlay during a drag would have made `commit` cancel the drag; a throwing `activate` would
   have left the tool active.
   - Changed: the manager takes the sticky error after every slot call, with a rule per slot (decision 11, "Errors").
4. **The external-cancel check missed an undo:** the serial moved only with `beginInteractive`, and an undo only
   cancels. Slots that commit, cancel or begin a command themselves, and nested modals, weren't covered.
   - Changed: the serial moves with begin, commit and cancel. The whole stack is checked before events and draws and
     after every slot. The manager acts on the modal it called, and a modal that finishes under others is an error.
5. **UE refuses undo while a transaction is open** (`EditorTransaction.cpp:1465-1474`). So S5's "undo during a drag
   cancels, then undoes the step before" couldn't happen with the adapter, and it contradicted coredcc's own rule (undo
   during a drag only cancels). Without the adapter, a UE undo during a drag reached no coredcc code.
   - Changed: S5 is defined for both configurations, and UnrealHistory cancels drags from `OnBeforeRedoUndo`.
6. **`popHead` through `Trans->Undo`** would undo whatever is on top (a UE edit), do nothing while a transaction is open,
   and broadcast a user undo.
   - Changed: `popHead` expires the change (`HasExpired`), which UE skips. `head()` is null unless UE's newest
     transaction is this history's and nothing was undone. S7 checks the interleaved case.
7. **Two precision tests were impossible.** `1e9 + 0.001` is already 4.7e-5 off in double, before any float. The drag's
   math at 1e9 comes back to 9.5e-7, not 1e-9 (measured: 9.3e-10 at 1e6, 2.2e-8 at 1e7, 5.4e-7 at 1e8).
   - Changed: the DrawList test checks the float stage against `float(p - origin)`; the drag tolerance is a few ulps of
     the coordinates' magnitude.
8. **S9's 1e-6 px against `FSceneView::WorldToPixel`:** UE computes it in float (`SceneView.cpp:1442-1446`).
   - Changed: 1e-6 px against a double reimplementation and 1e-3 against UE's; `UnscaledViewRect`, and the projection
     without TAA's jitter.
9. **Element undo couldn't store the mirrored partners' positions** (`gather` gives only the selected points), and a
   script's `setPositions` was read-only.
   - Changed: blocks with TransformableElements also implement ElementAccess, whose `positions` and `topoStamp` are
     used; `setPositions` is gated like a Command's `exec`, `undo` and `redo`.
10. **Symmetry with several axes had no rule** for an unselected point that is the partner of two moved points.
    - Changed: the source with the smallest set of axes wins, then the lower axis bits, then the lower handle.
11. **The gizmo's drawn median and the drag's pivot differed** when a parent and its child are both selected.
    - Changed: the median is over the objects that ApplyDelta moves, with a test.
12. **The DrawList's size limit:** a limit of 2³¹ on the count lets a record's u32 byte size overflow first.
    - Changed: limits by bytes.

### Gaps it found, now in the plan

  active (`settingsChanged`); colliding record ids (now the gizmo's id and the part); `begin` and `end` not bound for
  scripts; script tool instances counted in ForeignBindings; `runCommand` by `executor->running()`; drags begun without
  LastUsed values; a script facade for element drags.

  S11 for UE's other flags.

- `docs/index.md` gets the format document in step 8.
