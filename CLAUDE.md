# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

coredcc is a C++20 DCC foundation library on litestl. The design is
`docs/plans/2026-11-19-architecture.md`; progress and plan list is
`docs/implementation-tasklist.md`. `docs/index.md` lists all documentation; add new documents to it.

### Layout
- `source/coredcc/<module>/`: the library (include root is `source/`). `docs/modules.md` says what the
  modules are, what they depend on and where to start.
- `extern/litestl/`: litestl submodule. Its gitlink only ever points at litestl master; a
  pre-commit hook enforces this (`git config core.hooksPath tools/hooks` once per clone).
  litestl changes go up as PRs from this submodule checkout, never from `C:\dev\litestl`.
- `tests/`: native tests (litestl harness: `test_init`, `test_assert`, `return test_end()`),
  and `tests/compile_fail/`.
- `apps/testapp/`: NW.js integration test app, driven over CDP
  (`docs/plans/2026-11-19-test-app.md`).
- `cmake/CoredccHelpers.cmake`: `coredcc_library`, `coredcc_test`, `coredcc_compile_fail`.
- `tools/`: gates, benchmarks, the build cache, worktrees, the emsdk (`docs/building.md`).
  - Native builds share an sccache through `tools/cache.mjs`. Never run `sccache` by hand.
  - Make worktrees with `node tools/new-worktree.mjs <branch>`, and run `node tools/cache.mjs setup`
    after removing one.
  - Run benchmarks only with `tools/bench.mjs` and `tools/bench-bvh.mjs`: they build first.

### Build and test (native)
Run through `tools\devshell.cmd` (loads the VS 18 environment; from Git Bash prefer PowerShell,
or set `MSYS_NO_PATHCONV=1`). Presets: `native-clang` (clang-cl) and `native-msvc`, each
Ninja Multi-Config with `-debug` and `-release` (RelWithDebInfo) build/test presets.
- Configure: `tools\devshell.cmd cmake --preset native-clang`
- Build: `tools\devshell.cmd cmake --build --preset native-clang-debug`
- Test: `tools\devshell.cmd ctest --preset native-clang-debug`
- One test: `tools\devshell.cmd ctest --preset native-clang-debug -R test_base_signal`

### Gates
A skipped test is a failure in both.
- **Pre-commit:** `node tools/gate.mjs pre-commit`, before committing anything but documentation. Run it
  by hand; it is not a git hook. Builds and tests clang RelWithDebInfo (`native-clang-release`), with 5
  compile jobs or `--jobs N`. Logs are in `build/gate/`.
- **CI:** `.github/workflows/ci.yml` runs `node tools/gate.mjs ci` on GitHub, for each push to master and each
  pull request, unless only documentation changed. Don't run it all locally.
  - Builds and tests the four native presets (msvc/clang x debug/release), `wasm-st-debug` and
    `wasm-mt-debug`, and builds the benchmarks.
  - After a push, watch its run (`gh run watch`). If it fails, fix that before other work.
  - To reproduce a failure: `node tools/gate.mjs ci --only <preset>`. WASM needs the emsdk
    (`node tools/install-emsdk.mjs`), and `wasm-st-debug` also `npm ci` in `tests/wasm` and `pnpm install` in
    `apps/testapp`.

### Test app
`cd apps/testapp && pnpm install && pnpm test` (builds the page, runs `node:test` files that
launch NW.js on throwaway profiles). `pnpm run typecheck` type-checks page and tests.
Manual: `pnpm run launch`, then `node apps/testapp/cdp.mjs --port <port> call info`.

### Conventions
- No exceptions, no RTTI; errors are `coredcc::Status` / `Result<T>`.
- `/W4 /WX` on coredcc targets (`COREDCC_WERROR`); never let `source/` become a system
  include directory (the `warning_probe` compile-fail test guards this).
- No coredcc-owned global mutable state: registries live in a `Runtime`.

## Default rules

### Code comments

- Ordinary code comments (not doc comments) are at most 5 lines.
  - Exception: about one longer comment per 200 lines of code is allowed, for things like a
    section overview or an explanation of a tricky algorithm.
- Doc comments (docstrings, JSDoc, Doxygen, `///`, and the like) have no length limit.
- Math-heavy comments (derivations, formulas, numerical reasoning) have no length limit.
- Temporary comments have no length limit, but must start with `CLAUDENOTE:` so they can be
  found and stripped later (`grep -rn "CLAUDENOTE:"`).

### Documentation and plans

- Documentation goes in `docs/`.
- Plans go in `docs/plans/` and must be committed to the repo, not left in a scratch folder
  or only in the conversation.
- Pressure-test every plan before implementing it, which means trying to falsify it. Always
  do this in a fresh subagent: give it the plan and the code, but not your reasoning, so its
  attempt is not anchored on the author's view. Tell it to:
  - List the claims the plan depends on (about the code, the data, performance, APIs) and
    try to prove each one false: read the code, run a quick experiment, or find a
    counterexample.
  - Construct concrete inputs or scenarios that would make the plan fail.
- Record in the plan file which claims survived, which broke, and how the plan changed.
- Keep a running debugging guide in `docs/debugging.md`.

### File size

- When a source file grows past 35 KB, split it into smaller files.
- Split along real boundaries of responsibility, and give the pieces a subdirectory structure
  that reflects them (for example `parser/lexer.ts`, `parser/ast.ts`), not `foo1.ts` and
  `foo2.ts`.
- Generated files, vendored code, lockfiles, and data files are exempt.
